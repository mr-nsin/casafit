# CasaFit · api

ASP.NET Core Web API on .NET 10 LTS (C#), EF Core + Npgsql over Postgres. Identity is Supabase Auth (email one-time code, Google, Apple, Facebook); the API validates Supabase access tokens and issues none of its own.

See `docs/tech-stack.md` §2 and §3, `docs/architecture.md` §3 and `docs/decisions.md`.

> **Status.** Working: `GET/DELETE /v1/me` and the rest of `/v1/me/*` (plan, consents, export, sync), entitlements (consume, refund, status), the RevenueCat webhook, `GET /v1/content/version`, `GET /v1/content/packs/{name}`, `GET /healthz`, `GET /openapi/v1.json`. Not verified against a real Supabase project (none exists yet): tests sign tokens with a test secret and fake the admin API. Play Integrity / App Attest are not wired.

## How sign-in works

1. The app signs in with Supabase and sends `Authorization: Bearer <Supabase access token>`.
2. The API checks signature (HS256 with `Supabase__JwtSecret`, or ES256/RS256 against the JWKS at `Supabase__Url/auth/v1/.well-known/jwks.json`), issuer `Supabase__Url/auth/v1`, audience `authenticated`, expiry with 30 s skew.
3. On the first valid request the account is created from the claims (`sub` becomes `ExternalId`, `email` lower-cased, `app_metadata.provider` becomes `Provider`). The upsert is safe under concurrent first requests.
4. `DELETE /v1/me` deletes local data, keeps HMACs of the email and the Supabase user id for 180 days, then deletes the Supabase user through the admin API. If that call fails the response is a 502 problem (`code: identity_delete_failed`); local data is already gone, and repeating the request retries only the Supabase part.

## Configuration

Environment variables only; see `.env.example`.

| Variable | Meaning |
|---|---|
| `ConnectionStrings__Default` | Postgres. Npgsql form or a `postgres://` URL |
| `Supabase__Url` | Project URL, e.g. `https://abcd.supabase.co` (issuer, JWKS, admin API). Required |
| `Supabase__JwtSecret` | Legacy HS256 secret. Optional if the project uses asymmetric signing keys |
| `Supabase__ServiceRoleKey` | Admin API key used to delete users. Required outside Development. Server only |
| `RevenueCat__WebhookSecret` | Must equal the webhook `Authorization` header exactly. Empty rejects every webhook |
| `Auth__Pepper` | Server secret for hashing identifiers on the deleted-account list |
| `Content__Directory` | Folder with the content pack JSON files |
| `Database__MigrateOnStartup` | `true` to apply migrations at boot |
| `RateLimit__PerMinute` | Per-IP requests a minute across all endpoints (default 240) |
| `PORT` | Honoured when set (Railway, Cloud Run) |

The process refuses to start outside Development if `Auth__Pepper` is short or still starts with `change-me`, if `Supabase__Url` is not set, or if `Supabase__ServiceRoleKey` is empty.

## Content packs

`GET /v1/content/packs/{name}` serves `exercises`, `plans`, `foods`, `myths` and `concepts` (the last two are slices of `learn.json`). Any other name is a 404 problem. Responses carry a strong `ETag` and `Cache-Control: private, max-age=3600, must-revalidate`; `If-None-Match` gets `304`.

The files are not copied into git. Source of truth is `app/assets/content`:

- Local `dotnet run` (Development): `Content__Directory` defaults to `../../../app/assets/content`, relative to `src/CasaFit.Api`.
- Docker: the image copies the files into `/app/content` at build time and sets `Content__Directory=/app/content`. **The build context is the repo root**: `docker build -f api/Dockerfile -t casafit-api .` (compose does this for you).

## Run locally

With Docker (api + Postgres 16), from `api/`:

```bash
docker compose up --build
curl http://localhost:5080/healthz
```

Edit the `Supabase__*` values in `docker-compose.yml` first, or the API cannot verify tokens. To try the app against this API with no Supabase project, mint a dev token with `node api/tools/mint-dev-token.mjs` (HS256, compose secret, `dev@casafit.test`, 7 days) and set it as `EXPO_PUBLIC_DEV_AUTH_TOKEN` in `app/.env.local` (see `app/README.md`). Without Docker for the api, with Postgres running on localhost:

```bash
cd api
dotnet restore
dotnet run --project src/CasaFit.Api        # Development: http://localhost:5080, migrates on start
dotnet test                                 # integration tests start Postgres in Docker (Docker Desktop must be running)
```

Migrations (the `dotnet-ef` tool is a local tool, `dotnet tool restore` first):

```bash
dotnet dotnet-ef migrations add <Name> --project src/CasaFit.Infrastructure --startup-project src/CasaFit.Api --output-dir Persistence/Migrations
```

`SupabaseIdentity` (2026-10-30) drops phone login: it deletes every existing account row (dev databases only; there are no production users) and replaces the phone and OTP columns with `ExternalId`, `Email` and `Provider`.

Building writes `api/openapi.json`. Commit it when the contract changes, then update the zod types in `shared/src`.

## Deploy to Railway (Docker)

The image needs `app/assets/content`, so Railway must build from the **repo root**, not from `api/`.

1. New project, deploy from this repo. Service settings: root directory `/` (default), Config as code path `/api/railway.json` (sets the Dockerfile to `api/Dockerfile` and the health check to `/healthz`). Or set `RAILWAY_DOCKERFILE_PATH=api/Dockerfile`.
2. Add the Postgres plugin. Variables:

| Variable | Value |
|---|---|
| `ConnectionStrings__Default` | `${{Postgres.DATABASE_URL}}` |
| `Supabase__Url` | the Supabase project URL |
| `Supabase__JwtSecret` | only if the project still signs with the legacy HS256 secret |
| `Supabase__ServiceRoleKey` | the service_role key (secret) |
| `RevenueCat__WebhookSecret` | the same value as the RevenueCat dashboard webhook header |
| `Auth__Pepper` | 16+ random characters |
| `Database__MigrateOnStartup` | `true` (one instance) |
| `Content__Directory` | `/app/content` (already set in the image; override only if you mount your own) |

Railway sets `PORT` itself. Railway regions do not include Mumbai: use it for staging only; production data stays in India (see Cloud Run).

## Deploy to Cloud Run (asia-south1)

Cloud Run's `--source` build uses the folder you point at, so build the image from the repo root and deploy it:

```bash
gcloud builds submit --region asia-south1 --config - . <<'EOF'
steps:
  - name: gcr.io/cloud-builders/docker
    args: ["build", "-f", "api/Dockerfile", "-t", "asia-south1-docker.pkg.dev/PROJECT/casafit/api", "."]
images: ["asia-south1-docker.pkg.dev/PROJECT/casafit/api"]
EOF
gcloud run deploy casafit-api \
  --image asia-south1-docker.pkg.dev/PROJECT/casafit/api --region asia-south1 \
  --allow-unauthenticated --min-instances 1 \
  --set-secrets ConnectionStrings__Default=casafit-db:latest,Supabase__ServiceRoleKey=casafit-supabase-service:latest,Auth__Pepper=casafit-pepper:latest,RevenueCat__WebhookSecret=casafit-rc-webhook:latest \
  --set-env-vars Supabase__Url=https://YOUR-PROJECT.supabase.co,Database__MigrateOnStartup=true
```

- Cloud Run injects `PORT`; the app binds to it. The startup probe path is `/healthz`.
- Run migrations from CI rather than `Database__MigrateOnStartup` when there is more than one instance.
- Rate limiting is in-process per instance. Put a shared limiter in front if you scale out.

## CI

`.github/workflows/api.yml` restores, builds and runs unit and integration tests (Testcontainers needs Docker, available on `ubuntu-latest`). `.github/workflows/app.yml` runs `tsc --noEmit` and `jest` for the pnpm workspace.
