Login System & Multi-Device Sync

The OTP + JWT login system works in four steps:

Step 1
Send OTP
User submits phone or email. Server generates a 6-digit code with 5-minute TTL stored in Redis, sends via SMS (MSG91/2Factor.in).
Step 2
Verify Code
User enters code. Server verifies against Redis, creates or finds the account, returns JWT access + refresh tokens.
Step 3
Token Pair
Access token: 15 min, stateless JWT.
Refresh token: 30 days, stored per device in device_sessions.
Step 4
Offline Grace
7-day offline grace via cached session in SecureStore. 30-day refresh token ensures silent re-auth on reconnect.

Multi-Device Login

Each device gets its own independent token pair. A device_sessions table tracks all active sessions per account. Features:

  • Concurrent sessions: allow up to N devices (configurable, default 5)
  • Remote logout: user can revoke any device from Settings
  • Refresh rotation: each refresh token is single-use; replay detection revokes the entire family

Data Sync Across Devices

Pull-based sync (recommended for a workout app): each device calls GET /sync?since=<timestamp> on app open, and the server returns deltas.

India Data Residency

Railway and Render have no India region — nearest is Singapore. This fails DPDP Act compliance for the API/database layer. 4 Backend Architecture Patterns from the Industry

Common patterns observed in production fitness apps (based on case studies, job postings, and engineering blogs from apps serving 100K+ users):

Pattern 1
Domain Microservices
Each module (auth, workout, nutrition, analytics) runs as an independent service with its own database. Enables independent scaling and deployment. Used at scale by Peloton, Strava.
Pattern 2
Event-Driven Processing
Wearable syncs, AI pose analysis, and analytics run on async message queues (SQS, BullMQ, RabbitMQ). Prevents blocking user requests. Critical for form-check processing.
Pattern 3
Time-Series Health Data
Step counts, heart rate, and workout metrics stored in TimescaleDB or InfluxDB alongside the main Postgres. Enables efficient aggregation queries for progress charts.
Pattern 4
Content as Config
Workout plans, exercise libraries, and food databases served as versioned JSON manifests. App downloads the manifest + media pack once, plays sessions offline.

CasaFit Architecture — Recommended Approach

Start as a modular monolith (NestJS modules with clear boundaries), not microservices. Extract services only when a specific module needs independent scaling. This matches CasaFit's current team size and avoids premature complexity.

Key Insight

CasaFit's architecture is simpler than most fitness apps because pose analysis runs on-device (no GPU servers), workouts are offline-first (no streaming), and the food database is static.
